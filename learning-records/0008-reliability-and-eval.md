# 0008 — 可靠性与可观测性

## 学到了什么
- **四个维度**：护栏（不崩）、重试（不脆）、结构化日志（不瞎）、评测（不改坏）——互相依赖，不是四个独立功能
- **护栏三类**：步数上限（已有）、超时（AbortController）、token/费用预算（累计 usage）——触发后返回部分结果而非无声崩溃
- **重试纪律**：只重试瞬态故障（429/5xx/网络错误）、不重试确定性失败（400/401/业务错误）；只包裹 `client.responses.create()`，不重试整个 loop（避免重复副作用）；指数退避 1s→2s→4s，最多 3 次
- **结构化日志**：从人读 emoji 格式加一层机器可读 JSON（runId + outcome + timeline），支持事后统计和回放
- **评测集**：5–10 个行为回归用例，覆盖正常路径 + 无工具场景 + 边界输入 + 超出能力范围

## 为什么重要
Demo 能跑和生产能跑是两件事。LLM 的非确定性让"改 prompt → 某个 case 静默变坏"成为常态。护栏和评测是对抗非确定性的工程手段——前者限制破坏范围，后者在破坏发生时让你知道。

## 关键决策
- 超时用 AbortController 作用于单次 API 调用，而非整个 loop——细粒度控制
- 重试只包裹 `client.responses.create()`，不包裹工具执行——尊重副作用不可重复的约束
- 结构化日志作为 trajectory 的补充层，不替代人读格式——两者共存的方案
- 评测定位为行为回归（输入→输出模式断言），不是单元测试——测 Agent 的外部行为而非内部实现

## 待验证
- timeout 的实际效果（DeepSeek 代理的网络延迟分布）
- 重试退避时间是否过快打到 rate limit（429 需要更长的退避）
- 评测脚本是否能在 CI 中稳定跑（依赖外部 API 的稳定性）
