Lesson 0008 · 第 6 周

可靠性与可观测性：把 Agent 从"能跑"变成"跑不坏"

L5–L7 的 Agent 在正常情况下跑得很好。但生产环境不是 demo——网络会抖、 API 会超时、对话越来越长、改一个 prompt 可能会静默破坏之前正常的 case。 这一课教四件事：护栏、重试、 结构化日志、回归评测。

约 15–20 分钟 前置：L5 Loop + L7 Session 术语表

1. 四个维度一张图

维度解决的问题一句口诀你现在的状态
护栏 Agent 失控（超时/超步/烧钱） 让它死得干净 maxSteps 已有
重试 临时故障导致整个任务崩 不要因为打喷嚏就住院 无
结构化日志 出问题只能猜，看不到现场 让黑盒变白盒 trajectory 有人读格式
评测 改 prompt/工具后不知好坏 不改坏已知功能 无

四个维度不是四个独立功能——它们互相依赖： 护栏告诉你 Agent 什么时候出界了；日志记录出界时的上下文； 重试让你在出界前多给一次机会；评测确保你修了一个 bug 不会引入两个新的。

2. 护栏：不死、不超、不烧钱

你已经有了 maxSteps（loop.ts:38），但生产 Agent 需要三类护栏：

1. 步数上限（已有）

while (steps < maxSteps) — 防止无限 loop。但只有这个不够：模型可能在一步里生成 10KB 输出，或 API 响应等 60 秒。

2. 超时（缺失）

单次 API 调用超时 + 整体任务超时。网络抖动时，fetch 可能挂几分钟。AbortController 是答案。

3. Token / 费用预算（缺失）

每轮 response 返回 usage（input_tokens, output_tokens）。累积超过阈值就停——防止 prompt 被恶意注入无限对话。

4. 失败模式

护栏触发时应该返回部分结果（"我在第 3 步超时了，但完成了 1、2"），而不是无声崩溃。

面试考点：当面试官问你"你的 Agent 如何防止失控"时， 你应该能说出三类护栏的具体参数和触发后的行为——而不是"我设了 maxSteps=10"就完了。

3. 重试：不要因一个喷嚏就住院

当前 loop.ts 没有重试——client.responses.create() 失败 → 整个 runAgent 抛异常 → 调用方收到一个 Error，之前已完成的操作全部丢失。

什么值得重试？

可重试（瞬态故障）                不应重试（确定性失败）
═══════════════════              ══════════════════
• 网络超时 429 Rate Limit         • 400 Bad Request（参数错误）
• 5xx Server Error                • 401 Unauthorized（API key 错）
• 连接被拒绝 (ECONNREFUSED)       • Tool execute 返回的 Error（业务错误，不是故障）

三点重试纪律：

  1. 指数退避：间隔 = 1s → 2s → 4s → 8s，不是固定 1s
  2. 最大重试次数：通常 3 次，避免无底洞
  3. 只重试 API 调用本身，不重试整个 loop：loop 里已经有工具副作用了，重复整个 loop 会重复执行工具
为什么不能重试整个 loop？ loop 里的工具调用有副作用（改文件、发 HTTP）。 如果第 2 步的 API 调用失败了，你重试整个 loop——第 1 步的工具会再次执行，可能导致重复创建数据。 正确的做法是只在 client.responses.create() 这层加重试。

4. 结构化日志：让机器也能读你的执行轨迹

你现在的 formatTrajectory 是人读的 emoji 格式——适合 debug， 但如果你要做统计（"过去 100 次运行平均几步完成？哪个工具报错最多？"）， 需要对机器友好的格式。

不需要替换，需要加一层：

现状 
console.log(
  formatTrajectory(traj)
)
// ── Step 0 ──
// 🔧 todo_add(...)
// 💬 已添加...
加一层 
{
  "runId": "abc123",
  "startedAt": "...",
  "steps": 3,
  "outcome": "success",
  "timeline": [
    { "step": 0,
      "tool": "todo_add",
      "params": {...},
      "durationMs": 234 },
    ...
  ]
}

结构化日志的三个最低要求字段：runId（一次运行一个 UUID）、 outcome（success / max_steps / timeout / error）、 timeline（每步的工具+耗时+结果）。 有了这些，你可以用一行 jq 命令统计失败率。

面试叙事：不要说"我做了日志"。说"我的 Agent 每条轨迹有结构化日志， runId 关联一次完整运行，outcome 字段标记终止原因——所以我可以回放任何一次失败， 不需要用户重现。"这揭示了你的生产思维。

5. 评测：改一行代码，跑一遍回归

你改了一段 prompt、加了一个工具、调整了 maxSteps——这些改动可能静默破坏 之前正常的 case。没有评测，你只能靠"感觉"。

最小可行评测集应该长什么样：

用例名输入断言什么
add_single_todo 添加待办：买菜 outputText 包含"已添加"；至少调用 1 次 todo_add
list_all_todos 列出所有待办 至少调用 1 次 todo_list；trajectory 中无 function_call 报错
unknown_tool 帮我订机票 outputText 不崩溃；明确告知"无法完成"或要求补充
multi_step_plan 帮我规划本周任务 steps ≥ 2；outputText 包含"总结"或"完成"
empty_input （空字符串） 不抛异常；outputText 不为空（合理处理边界输入）

这些不是单元测试（不测内部逻辑），是行为回归测试—— 验证 Agent 对某个输入的输出符合预期模式。重点是覆盖： 正常路径 + 无工具场景 + 边界输入。

7. 练习

以下练习只描述目标，代码由你实现。

  1. 超时护栏：给 runAgent 加 timeoutMs 选项。用 AbortController 控制单次 API 调用超时（不是整个 loop）。 超时后返回部分结果 + outcome = "timeout"，不要直接崩。
  2. 重试装饰器：在 src/Agent/ 下新建 retry.ts， 写一个通用重试函数（接收 async fn + 配置，返回带重试的 fn）。 遇到 429 / 5xx / 网络错误时自动重试，最多 3 次，指数退避（1s → 2s → 4s）。 只包裹 client.responses.create()，不重试整个 loop。
  3. 结构化日志：改造 runAgent，除了返回 trajectory 数组， 额外输出一份 JSON 格式的 RunLog（含 runId、outcome、timeline）。 timeline 中每步包含 tool 名、参数、耗时 ms、成功/失败。
  4. 评测脚本：在项目根目录新建 eval/ 目录，写一个 eval/suite.ts 脚本。定义 5–10 个测试用例（至少覆盖： 添加待办、查询、无效工具请求、空输入）。每个用例跑一次 runAgent， 用简单断言（字符串包含 / 不抛异常 / steps 范围）验证。脚本输出通过/失败统计。
提示：评测脚本可以复用 main.ts 的 registry 和 instructions 初始化逻辑， 但注意每个用例之间清空待办数据（todos.json）。
