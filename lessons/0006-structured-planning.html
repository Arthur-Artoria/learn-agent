结构化计划与轨迹：让 Agent 先想清楚再动手

L5 的 Agent Loop 会跑了，L6 的工具能写文件了。但遇到「帮我规划本周任务」这种复杂请求时， 模型是一边想一边干的——结果可能是漏步骤、重复操作、或者说不清自己干了什么。 这一课教两件事：用 instructions 强制先计划再行动，以及 把 loop 的轨迹变成可读的执行报告。

约 12–15 分钟 前置：L5 Agent Loop + L6 工具工程 术语表

1. 两种 Agent 思维模式

反应式（L5 现状） 
用户: "规划本周任务"
模型: 调用 todo_add("写周报")
模型: 调用 todo_add("开会")
模型: 调用 todo_list()
模型: "我帮你加了写周报和开会"
// 问题：没有全局视角，
// 可能漏掉重要任务，
// 用户不知道它到底做了什么
计划驱动（目标） 
用户: "规划本周任务"
模型: "我来分析一下：
      1. 先看现有待办
      2. 补充本周必做项
      3. 按优先级排列"
模型: todo_list()
模型: todo_add("写周报")
模型: todo_add("项目评审")
模型: "已完成规划，新增2项..."
// 用户能看到逻辑链条

区别不是「有没有用工具」，而是模型在动手前是否先输出了一个可审计的计划。 这个计划让用户和开发者都能理解 Agent 在做什么、为什么这样做。

2. 用 instructions 驱动计划行为

runAgent 已经有 instructions 参数（loop.ts:45）。 关键是写什么样的 instruction 能稳定产出计划： 

const instructions = `你是一个任务管理助手。对于任何涉及 2 个及以上操作的请求，
你必须遵循以下流程：

1. **分析**：先理解用户意图，列出需要哪些步骤
2. **执行**：按步骤依次调用工具，每步完成后确认结果
3. **总结**：最后汇总做了什么、结果如何、是否有遗留问题

在开始执行前，先用文字输出你的计划。
如果某一步失败，说明失败原因并尝试替代方案。`;

三条 instruction 设计原则：

  1. 具体而非笼统：别说"好好干"，说"先 X 再 Y 最后 Z"
  2. 给失败预案：告诉模型工具失败时该怎么做（重试？跳过？问用户？）
  3. 约束输出格式：让模型用编号、小节等结构化方式输出，方便人读
面试加分点：当面试官问「你怎么确保 Agent 行为可预测」时， 答案不是"调 temperature"，而是"在 instructions 里约束行为模式，并用 trajectory 验证"。

3. 轨迹可视化：让黑盒变白盒

你现在的 runAgent 返回 trajectory（每一步的 output 数组）， 但直接 console.log 是一大坨 JSON。把它格式化成可读报告： 

// 格式化 tool call
🔧 todo_add({ title: "买牛奶" })
  → 已添加待办: [todo_xxx] 买牛奶

// 格式化工具错误
🔧 todo_complete({ id: "bad_id" })
  ❌ Error: 未找到 id 为 "bad_id" 的待办事项

// 格式化模型消息
💬 已添加 3 条待办，目前共 5 条...

一个好的 trajectory 报告回答三个问题： Agent 做了什么（工具调用序列）、 每一步结果如何（成功/失败/数据）、 为什么这样做（模型在每个决策点的推理）。

这不是花活，是工程需求：当 Agent 行为异常时， trajectory 是你唯一能还原现场的东西。没有它，你只能猜。

5. 练习

  1. 写一套 instructions：在 main.ts 里给 runAgent 传入符合三原则的 instructions，让 Agent 在处理多步任务时先输出计划。
  2. 实现 trajectory 格式化函数：在 src/Agent/ 下新建 trajectory.ts，把 trajectory 数组格式化为可读报告。 区分 function_call、function_call_output、message 三种输出类型。
  3. 用一个包含 3+ 步骤的请求验证（如「分析我的待办、补充遗漏项、按优先级排序」）， 确认输出中包含清晰的计划 + 轨迹报告。
