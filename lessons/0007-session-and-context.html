Lesson 0007 · 第 4 周

会话状态与上下文压缩：让 Agent 记住你是谁

L5 的 runAgent 每次都从零开始——它不记得上一轮说了什么、做了什么。 这一课解决两件事：如何在多次调用间保持对话连续性，以及 当对话太长时如何压缩而不丢失关键信息。

约 15–20 分钟 前置：L5 Agent Loop + L6 工具工程 术语表

1. 每次见面都像第一次

打开 src/Agent/loop.ts:27-32，看 currentInput 的初始化： 

const currentInput: ResponseInput = [
  {
    role: 'user',
    content: input,   // ── 永远只有当前这一条
  },
]

这意味着三次独立的 runAgent 调用之间完全没有关联。 你问「帮我添加待办：买牛奶」，它加了。再问「我刚才让你加什么来着？」——它不知道。

这不是 bug，是当前架构的设计取舍：loop 是纯函数，输入决定输出。 无状态让测试和推理变得简单。但交付一个生产力工具，状态是必须的。

2. 两条路径：server-side 还是 client-side？

previous_response_id 自管 history（推荐）
原理 告诉 OpenAI "续接上一次响应"，平台替你记住历史 你自己在 currentInput 数组里维护所有历史消息
好处 一行代码，平台自动处理 完全透明可控；可序列化持久化；不绑平台
坑 黑盒——你看不到历史内容；换平台就丢；和 Loop 的 tool 拼接逻辑冲突 你要自己管理数组长度和 token 预算
适合 快速原型、简单 Chat UI Agent Loop（本课程路径）

你已在 L4 中用过 previous_response_id（FunctionCalling.ts）， 也在 L5 中选择了手动拼接 input。现在要继续这个方向：维护一个跨调用的 conversation 数组。

核心思路：把 runAgent 的职责从「接收一条输入 → 返回结果」升级为 「接收一条输入 + 现有上下文 → 返回结果 + 更新后的上下文」。

3. Context Budget：对话不扣预算，迟早会炸

每轮对话追加 user message + assistant output + function_call + function_call_output…… 数组只增不减。几十轮之后，你的 currentInput 可能有几万 token。

不控制 
第 50 轮:
currentInput.length = 800
→ 超出模型 context window
→ API 报错或截断
有节制 
第 50 轮:
currentInput.length = 30
→ 始终在预算内
→ 对话流畅，成本可控

两个预算维度：一是模型最大 context window（硬上限，超了就报错）， 二是实际成本（每 1K token 都花钱，历史越长越贵）。 好的 Agent 要同时控制两者。

DeepSeek 的 context window 通常为 128K token，但越靠近上限质量越差（lost-in-the-middle 效应）。 建议实际使用预算保持在 window 的 50–70% 以内。

4. 三种压缩策略

压缩的本质是用一个更短的表示替代一段历史，同时保留影响后续决策的关键信息。

策略 A

滑动窗口 (Sliding Window)

只保留最近 N 条消息（如最近 20 条）。实现最简单，但会丢掉"对话开头你告诉我的偏好"这类远期信息。

策略 B

摘要压缩 (Summarization)

当对话超过阈值时，调用模型把早期对话压缩成一段摘要，用摘要替代原始消息。保留语义，丢失细节。

策略 C（推荐）

摘要 + 近期窗口

摘要保存远期背景，最近 N 条消息保持原样。兼顾长期记忆与短期精度。这是多数生产 Agent 的方案。

策略 C 的数据结构大致长这样：

{
  "summary": "用户叫小王，在做一个任务管理Agent。
               之前讨论过用 JSON 文件做数据库。",
  "recent": [
    { "role": "user", "content": "添加待办：买牛奶" },
    { "role": "assistant", "content": "..." },
    { "type": "function_call", ... },
    { "type": "function_call_output", ... },
    // 最近 20 条保持原样
  ]
}

每次追加新消息后检查：如果 recent 长度超过阈值，就用模型把最早的一批消息压缩进 summary，然后从 recent 里删掉它们。

面试加分点：当面试官问「你怎么处理长对话」，不要只说"用滑动窗口"。 讲清楚三种策略的 trade-off，以及你为什么选择摘要 + 窗口的混合方案——这说明你做的是工程决策，不是抄模板。

6. 练习

以下练习只描述目标，不提供实现代码——你需要自己写。 完成后可以用 bun run src/main.ts 验证。

  1. 会话持久化：新建 src/Agent/session.ts，实现一个 SessionManager 类。它负责把 conversation 数组（即 ResponseInput）持久化到本地 JSON 文件， 支持 save 和 load。每个会话用唯一 ID 区分。
  2. 改造 runAgent：让 runAgent 接受一个可选的 conversation 参数 （而不是内部初始化为空数组）。调用侧负责传入上一次保存的 conversation。 新消息执行完毕后，把更新后的 conversation 返回给调用侧。
  3. 上下文压缩：在 session.ts 中实现三种压缩策略之一的 compress 方法： 当 conversation 消息数超过阈值（如 30 条），自动压缩。 建议从滑动窗口开始，跑通后再升级到摘要方案。
  4. 端到端验证：在 main.ts 中写一个多轮对话场景 （如：先加 2 条待办 → 再问"我刚才加了什么"→ 再添加 1 条 → 列出全部）。 关闭进程再重启，验证能接着上次对话继续。
提示：第 4 步验证"重启后恢复"是关键验收点。如果关了进程就全丢了， 说明 session 没有正确落盘或加载。检查 JSON 文件的读写路径和序列化格式。
